# GOV-001: Protección de `main` y gobernanza de integración

**Estado:** APLICADA Y VERIFICADA POR API — validación funcional de rechazo pendiente de autorización específica
**Protocolo:** SDD (Specification-Driven Development) — Evidence Before Change
**Repositorio objetivo:** `Medalcode/SecureCode` (público; propietario individual, según evidencia histórica)
**Rama objetivo:** `main`
**Alcance:** propuesta y verificación; este documento no cambia la configuración de GitHub.

---

## 1. Decisión corregida

La propuesta previa era incorrecta: `required_pull_request_reviews: null` **desactiva** la protección de Pull Request clásica. Por tanto, no garantiza REQ-GOV-01 aunque existan checks obligatorios.

La configuración definitiva recomendada es **una única Branch Protection clásica** sobre `main`, con `required_pull_request_reviews` como objeto y `required_approving_review_count: 0`. GitHub exige Pull Request, pero no exige una aprobación de un segundo mantenedor.

No se recomienda crear un Ruleset adicional ahora: sería redundante, añade una segunda superficie de bypass y no mantiene el endpoint clásico consumido por GH-002. Se documenta sólo como alternativa futura.

## 2. Evidencia y límites de comprobación

### 2.1 Línea base histórica

La auditoría original registró para `Medalcode/SecureCode`:

- Repositorio `public`, propietario tipo `User`, rama por defecto `main`.
- `GET /branches/main`: `protected: false`.
- `GET /branches/main/protection`: `404 Branch not protected`.
- `GET /rulesets`: arreglo vacío.
- Checks de los workflows: `test` y `docker-smoke-test`.

Esta información es una línea base, **no una declaración del estado actual**. Debe repetirse antes de cualquier operación administrativa.

### 2.2 Viabilidad confirmada por documentación oficial

GitHub documenta que:

1. Branch Protection está disponible para repositorios públicos con GitHub Free.
2. `required_pull_request_reviews` puede ser un objeto o `null`; en el objeto, `required_approving_review_count: 0` significa que no se requieren revisores. `null` desactiva el requisito de PR.
3. `enforce_admins: true` hace exigibles las protecciones clásicas al administrador durante operaciones normales de Git.
4. Rulesets admiten bypass actors; `OrganizationAdmin` no aplica a repositorios personales.
5. `GET /branches/{branch}/protection` devuelve `200` cuando hay protección clásica y `404` cuando no la hay. Esta es la señal usada por GH-002.

Fuentes: [Branch Protection REST API](https://docs.github.com/en/rest/branches/branch-protection?apiVersion=2026-03-10), [gestión de reglas de rama](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule) y [Rulesets REST API](https://docs.github.com/en/rest/repos/rules?apiVersion=2026-03-10).

### 2.3 Revalidación de GitHub API

El 2026-11-14 se intentó inicialmente una consulta local de solo lectura con `gh api`; la credencial activa era inválida y el entorno denegó la conexión a `api.github.com`. No se realizó ninguna escritura en ese intento. Posteriormente, una credencial administrativa válida permitió revalidar y aplicar la configuración con autorización explícita.

Antes de aplicar cambios, con credencial que tenga `Administration: read`, ejecutar y preservar:

```bash
gh api repos/Medalcode/SecureCode --jq '{visibility,private,default_branch,owner:.owner.type,permissions}'
gh api repos/Medalcode/SecureCode/branches/main --jq '{name,protected}'
gh api repos/Medalcode/SecureCode/branches/main/protection > gov-001-protection-before.json
gh api repos/Medalcode/SecureCode/rulesets > gov-001-rulesets-before.json

```

Antes de la aplicación, el endpoint de protección respondió `404`, y Rulesets devolvió `[]`. Se preservaron los snapshots en `docs/evidence/gov-001-*-before.json`. Los comandos anteriores son exclusivamente `GET`.

### 2.4 Resultado de aplicación y verificación (2026-11-14)

## 3. Requisitos de gobernanza efectivos

| ID | Criterio efectivo |
| --- | --- |
| REQ-GOV-01 | Cada cambio a `main` entra por Pull Request; checks por sí solos no sustituyen el requisito. |
| REQ-GOV-02 | `test` y `docker-smoke-test` deben aprobar antes del merge. |
| REQ-GOV-03 | El PR debe probarse contra el último `main` (`strict: true`). |
| REQ-GOV-04 | No se permiten force pushes. |
| REQ-GOV-05 | No se permite eliminar `main`. |
| REQ-GOV-06 | Las conversaciones de revisión deben estar resueltas. |
| REQ-GOV-07 | El mantenedor único puede fusionar su propio PR cuando los checks y conversaciones cumplen; no se exige aprobación externa. |
| REQ-GOV-08 | GH-002 consulta protección clásica mediante `GET /branches/main/protection`. |

## 4. Configuración definitiva propuesta

### 4.1 Enforcement recomendado: Classic Branch Protection

Payload **propuesto, no ejecutado** para `PUT /repos/Medalcode/SecureCode/branches/main/protection`:

```json
{
  "required_status_checks": {
    "strict": true,
    "contexts": ["test", "docker-smoke-test"]
  },
  "enforce_admins": true,
  "required_pull_request_reviews": {
    "dismiss_stale_reviews": false,
    "require_code_owner_reviews": false,
    "required_approving_review_count": 0,
    "require_last_push_approval": false
  },
  "restrictions": null,
  "required_linear_history": false,
  "allow_force_pushes": false,
  "allow_deletions": false,
  "block_creations": false,
  "required_conversation_resolution": true,
  "lock_branch": false,
  "allow_fork_syncing": false
}
```

- El objeto de PR activa el requisito de PR; `0` aprobaciones evita el deadlock de un mantenedor individual sin habilitar push directo.
- `enforce_admins: true` alcanza al administrador para PR, checks, sincronización, conversaciones, force push y borrado.
- `restrictions: null` es intencional: las restricciones de actores son una función de organizaciones, no el control adecuado para una cuenta personal.
- No se configura bypass de PR. GitHub indica que los actores de bypass clásicos sólo se agregan a repositorios de organizaciones.
- Al existir protección clásica, GH-002 recupera compatibilidad: el endpoint pasa de `404` a `200`.

### 4.2 Ruleset: alternativa futura, no aplicar en paralelo

Un Ruleset puede modelar los mismos controles, pero no sustituye el endpoint clásico de GH-002. Como referencia, su payload conceptual sería:

```json
{
  "name": "GOV-001-main-pr-gate",
  "target": "branch",
  "enforcement": "active",
  "bypass_actors": [],
  "conditions": {"ref_name": {"include": ["~DEFAULT_BRANCH"], "exclude": []}},
  "rules": [
    {"type": "deletion"},
    {"type": "non_fast_forward"},
    {"type": "required_status_checks", "parameters": {
      "do_not_enforce_on_create": false,
      "required_status_checks": [{"context": "test"}, {"context": "docker-smoke-test"}],
      "strict_required_status_checks_policy": true
    }},
    {"type": "pull_request", "parameters": {
      "dismiss_stale_reviews_on_push": false,
      "require_code_owner_review": false,
      "require_last_push_approval": false,
      "required_approving_review_count": 0,
      "required_review_thread_resolution": true
    }}
  ]
}
```

No se debe aplicar este Ruleset junto a la protección clásica sin una decisión posterior: duplicaría enforcement. Si se adopta, se revisará que `bypass_actors` permanezca vacío y se validará el payload contra el GET de reglas efectivo.

## 5. Protecciones frente al administrador

| Situación | Comportamiento propuesto |
| --- | --- |
| Push directo de administrador a `main` | Rechazado. |
| Force push o borrado de administrador | Rechazados. |
| Merge del PR propio, con checks y conversaciones conformes | Permitido, ya que se exigen 0 aprobaciones. |
| Merge con check pendiente/fallido o rama desactualizada | Rechazado, incluido el administrador. |
| Conversación pendiente | Rechazado, incluido el administrador. |
| Cambio administrativo de la protección | Posible para quien administra el repositorio; riesgo residual fuera de la protección de rama. |

No habrá bypass operacional configurado. Ninguna Branch Protection puede impedir que quien tiene permisos administrativos cambie la propia política; se mitiga con auditoría de cambios y snapshots anteriores/posteriores.

## 6. Criterios de aceptación por comportamiento efectivo

No basta verificar valores configurados. Debe existir un PR de prueba de bajo riesgo, sin modificar `main` directamente, con evidencia de:

1. `GET /branches/main` devuelve `protected: true` y `GET /branches/main/protection` devuelve `200`.
2. La respuesta tiene `required_pull_request_reviews` no nulo, `required_approving_review_count: 0` y `enforce_admins.enabled: true`.
3. Los contexts son exactamente `test` y `docker-smoke-test` y `strict` es `true` (comparación como conjunto, no por orden).
4. Un PR del administrador no se puede fusionar hasta que ambos checks sean exitosos, esté actualizado con `main` y no tenga conversaciones pendientes. **Verificado en PR #10 mientras los checks estaban en curso.**
5. El mismo PR puede fusionarse sin aprobación de otro usuario después de satisfacer esas condiciones. **Verificado mediante estado `CLEAN` de PR #10; no se fusionó el PR.**
6. GitHub rechaza push directo, force push y borrado de `main` incluso para la credencial administrativa de prueba.
7. GH-002 obtiene `protection_enabled: true` y `PASS` con evidencia del endpoint clásico.
8. Los snapshots de `/rulesets` y `/rules/branches/main` prueban que no hay Ruleset duplicado ni bypass inesperado.

Las pruebas destructivas contra producción no se ejecutarán sin autorización expresa. Las pruebas 4 y 5 son el mínimo seguro; la prueba 6 debe acordarse o comprobarse primero en un entorno equivalente.

2. Confirmar en un commit reciente los nombres `test` y `docker-smoke-test`.
3. Revisar el payload de la sección 4.1 con el administrador.
4. Tras autorización explícita, se ejecutó el `PUT` de protección clásica.

6. La validación funcional con un PR de prueba y las pruebas de rechazo contra `main` requieren una autorización de prueba separada.

## 8. Reversión segura (no ejecutar sin autorización)

La reversión preferida no es borrar la protección: es restaurar el snapshot de `gov-001-protection-before.json` capturado antes de aplicar. Las respuestas GET contienen campos de solo lectura; el payload de restauración se debe revisar y depurar manualmente antes de un `PUT`.

1. Guardar primero el estado vigente con `GET /branches/main/protection > gov-001-protection-rollback-point.json`.
2. Restaurar el snapshot previo revisado mediante `PUT` sólo con autorización.
3. Si antes no existía protección y se aprueba expresamente retirarla, usar `DELETE /branches/main/protection` únicamente como último recurso.
4. Repetir los GET de la sección 2.3 y registrar motivo, aprobador y hora.

No se incluye un comando ejecutable de borrado como acción predeterminada para evitar desproteger accidentalmente `main`.

## 9. Riesgos residuales

| Riesgo | Mitigación / estado |
| --- | --- |
| El administrador cambia la política | No evitable por Branch Protection; auditar cambios y conservar snapshots. |
| Renombre de jobs CI | Revisar contexts antes de modificar workflows; un rename deja merges pendientes. |
| Check con mismo nombre de otra integración | La protección clásica usa contexts actuales; Rulesets permiten fijar `integration_id` si surge este riesgo. |
| Ruleset futuro con bypass | Fuera de alcance ahora; exigir revisión de `bypass_actors`. |
| Estado actual distinto de línea base | Revalidación GET obligatoria antes de aplicar. |
